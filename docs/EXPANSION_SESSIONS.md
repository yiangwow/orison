## Purpose

ORISON will grow through focused development sessions rather than one large
rewrite. Each session should add one meaningful layer, preserve ambiguity, and
leave the repository in a state from which another session can continue without
chat history.

This document is the canonical specification for ORISON milestones and expansion
sessions, not visitor-facing canon. It defines interaction goals, boundaries,
validation, and sequencing. `ROADMAP.md` summarizes this sequence and
`docs/CURRENT_STATE.md` records its delivery state; neither independently
redefines a milestone. This document does not settle ORISON's origin, location,
body, purpose, or final story.

## Session continuity test

Every expansion session begins as if prior chat context is unavailable.

Before editing, the session must:

1. Read `AGENTS.md`, `VISION.md`, `ARCHITECTURE.md`,
   `docs/CURRENT_STATE.md`, this file, `ROADMAP.md`, and relevant ADRs.
2. Inspect the current branch, open pull requests, merged pull requests, and
   deployed-state notes.
3. State the selected milestone, what is explicitly out of scope, and the
   visitor-facing effect in a short bounded plan.
4. Verify the current critical journey before changing it.
5. Use a fresh feature branch whose earlier pull request has not been merged.

If a new session cannot recover the intended next task from these files, the
continuity system has failed and the documents must be repaired before feature
work begins.

At the end of every session:

1. Run the milestone-specific tests and the shared regression contract.
2. Review desktop, narrow-mobile, keyboard, and reduced-motion behavior.
3. Capture screenshots for visual work and critique whether the result feels
   authored, restrained, and specific to ORISON.
4. Update `docs/CURRENT_STATE.md` with implementation, validation, deployment,
   and blockers.
5. Update architecture, vision, roadmap, and ADRs only where their accepted
   truth changed.
6. Commit with the owner's git identity, push the feature branch, open
   and verify a pull request, and inspect checks before reporting completion.
7. Deploy only after merge and verify the public journey separately.

## Shared creative rules

- The first terminal is already strong. Preserve its restraint and realism.
- Motion must communicate process, attention, prediction, retention, or scale.
  Do not add random glitch loops merely to keep pixels moving.
- Interaction must change interpretation or system state. Decorative hover
  animation does not count as a milestone.
- Present evidence rather than explaining the premise. Do not tell the visitor
  that the archive is an examination or summarize ORISON's strategy before an
  earned late-state inversion.
- Never address the visitor as `you` or `your`. Visitor-facing records use
  subject, observer, source, order, operator, or the trace designation.
- Use real systems vocabulary only where the interface performs or represents a
  corresponding operation.
- Keep the one-time mechanical apertures rare, transient, and non-replayable.
- Add no gore, jumpscares, scream audio, fake compromise claims, or invasive
  permissions.
- Preserve first-party local state and the accepted privacy boundary unless a
  new ADR explicitly changes it.
- Prefer deepening an existing route over adding a route that contributes no new
  interaction or inference.

## Milestone 1: Living Archive

Status: Implemented, merged, and deployed

### Objective

Make the recovered directory feel like active infrastructure rather than a
finished poster. The visitor should sense ongoing process before any explicit
manifestation appears.

### Visitor-facing effect

- Background systems drift, desynchronize, pause, and reclassify themselves.
- The directory reacts to hover, focus, hesitation, keyboard selection, and
  pointer departure.
- Different recovered objects disturb different parts of the underlying process
  field.
- The response implies that the archive notices attention, not merely clicks.

### Candidate interactions

- Process rows advance at unequal intervals and occasionally enter a waiting or
  uninterruptible state.
- Hovering one object reroutes or suppresses related background processes.
- Sustained dwell changes a file's operational state without immediately
  changing its visible title.
- Keyboard focus produces the same semantic response as pointer hover.
- Leaving and returning to the tab produces a small retained interrupt or
  resumed-watchdog event.
- A selected object's residue may remain briefly after the pointer leaves.

### Boundaries

- Do not make every element pulse or move.
- Do not replay or emphasize the mechanical apertures.
- Do not add a new cookie field unless the interaction requires durable meaning.
- Do not add the digital horizon, a new recovered object, or expanded sound in
  this milestone.
- Do not turn process text into a readable lore dump.

### Success criteria

- The archive visibly changes over 20–40 seconds without visitor input.
- Interaction alters the process field in a way specific to the selected object.
- A visitor can notice responsiveness before opening a room.
- The effect remains sparse enough that the document hierarchy is dominant.
- Mobile does not overflow, obscure links, or become visually noisy.
- Reduced motion preserves state changes while removing continuous drift.

### Implemented result

- Unequal process schedulers advance through running, waiting, sleeping, and
  uninterruptible states.
- Each recovered object disturbs a specific pair of process rows.
- Hover and keyboard focus share one attention path.
- Dwell reclassifies the selected object temporarily; departure leaves a brief
  retained residue.
- Returning to the tab records a watchdog interrupt.
- Continuous column drift is removed under reduced motion while discrete state
  changes remain.
- No new route, cookie field, dependency, permission, sound, or privacy behavior
  was added.

## Milestone 2: Deeper Mutations

Status: Implemented, merged, and deployed

### Objective

Make revisiting existing rooms produce stronger differences based on what the
visitor previously did, in which order, and after how much absence.

This historical Milestone 2 planning text referred to cookie-backed continuity;
the current store is the version-2 `localStorage` record. A revisit may
feel like a different operational condition of the same route: page composition,
record relationships, available controls, visual scale, and apparent document
authority may change substantially. Do not limit mutations to counters, one
revised sentence, or a small status label.

### Candidate mutations

- Root terminal recognizes particular completed operations rather than only a
  broad awareness level.
- The inode changes ownership language according to invitation, return order,
  and operator access.
- Archive ordering, grouping, and negative space change according to the first
  room opened, while retaining enough anchors to reveal that the same directory
  has been reclassified.
- Camera 06 may return as a different reconstruction mode, with later-route
  residue changing the dominant composition rather than only its caption.
- Weather may replace the readable forecast with a post-event reconstruction
  that treats an action taken after the first visit as archived evidence.
- Choir may shift between transcript, carrier-control, and retained-silence
  states according to first output, later return, and elapsed absence.
- Staff and dead-letter records may exchange ownership of the page, remove or
  expose controls, and contradict one another without explaining which is
  authoritative.
- Missing-path responses react to the shape and timing of prior probes.

### Boundaries

- Each mutation must add a new inference, not display a larger counter.
- Do not make every page change on every visit.
- Large changes are encouraged when earned by explicit cookie state, but preserve
  at least one stable anchor per route so visitors can recognize what changed.
- Drastic does not mean random: every replacement, reflow, disappearance, or
  contradiction must trace to a documented visit-order, flag, return, or
  elapsed-time condition.
- Implement explicit state flags for durable events; do not overload awareness.
- Version and migrate any cookie schema change; keep all state first-party and
  local.

### Success criteria

- At least three existing routes gain distinct first-visit and revisit states.
- Visit order produces at least one meaningful branch.
- At least two revisit states materially change page composition or interaction,
  not only copy.
- At least one late-state page should feel startlingly unlike its fresh state
  while remaining clearly connected to it.
- A fresh trace still receives the original coherent journey.
- Existing version-1 traces migrate or remain valid without silent loss.

### Implementation record

  traces with three retained answers resume at question four instead of losing

  mount remains the final operation of the same examination session.

## Milestone 5: Digital Horizon

Status: Implemented, merged, and deployed

### Objective

Create the first major change of scale: a finite foreground structure against
an apparently unbounded field of green system language.

### Composition

- Foreground: dark city, gantry, tower, corridor, platform, or machine-complex
  silhouette with at least one human-scale cue.
- Background: receding process text, addresses, observer residue, or operational
  language behaving as atmosphere rather than readable exposition.
- Motion: extremely slow depth drift or parallax, with a deliberate still
  reduced-motion composition.
- Copy: little or none.

### Narrative possibilities to preserve

- an interior world inside the archive;
- network topology perceived as architecture;
- remembered or simulated city;
- infrastructure behind the visible interface;
- metaphorical scale;
- literal scale.

No implementation may confirm one interpretation.

### Trigger questions to decide in that session

- Is the horizon a new route, a state-earned rupture, or a transient replacement
  of an existing page?
- Which prior action earns it?
- Can it be revisited, and if so, what is lost by replay?
- Does it precede or follow the operator scene?
- Does it write a durable flag?

These questions are intentionally unresolved until the milestone begins.

### Boundaries

- Do not use the horizon as a recurring site background.
- Do not combine it with the aperture manifestation.
- Do not place a clear ORISON face or body in the scene.
- Do not make all background text readable.
- Do not add explanatory captions.

### Success criteria

- The scene materially changes the perceived scale of ORISON.
- A screenshot communicates foreground/background depth without relying on
  animation.
- Motion adds depth rather than visual noise.
- Mobile preserves the finite foreground and immense field relationship.
- The scene enlarges interpretation instead of narrowing it.

  revisits remain available as a deliberate still; Operator does not force the

## Milestone 7: Local Trace and Observation Audit

Status: Implemented, merged, and deployed

### Objective

Reassess what ORISON can responsibly retain about a visitor and expand
interaction-derived continuity where it materially deepens the experience.
The goal is more behavioral specificity without identity collection,
fingerprinting, or hidden surveillance.

Browser storage permits more authored continuity than ORISON currently uses,
but “stored in the user's browser” does not automatically mean “never leaves the
browser.” The current `Path=/` cookie is attached to matching requests to
`orison.zip`, is readable by page JavaScript, and has a small practical size
budget. `localStorage` is not attached to HTTP requests and may be a better home
for larger strictly local narrative state, but adopting it would change the
accepted persistence architecture and requires an ADR, migration, erasure, and
privacy review.

### Retention candidates

Prefer observations produced inside ORISON:

- coarse dwell bands per recovered object rather than exact pointer traces;
- pointer, touch, and keyboard interaction counts or dominant modality;
- recognized command categories and refused-command counts, never raw terminal
  strings or arbitrary keystrokes;
- answer consistency, answer revision, and checksum outcomes;
- route-order branches, revisit intervals, return methods, and coarse absence
  bands;
- which controls were ignored, retried, opened in parallel, or revisited;
- invitation progression and whether a witness route was followed.

Keep coarse environment fields ephemeral unless a separate decision proves a
durable narrative need. Browser family, platform family, language, timezone,
screen and viewport dimensions, processor count, approximate memory, touch
points, contrast, and motion preference are currently rendered but not
persisted. Do not silently turn that temporary profile into a fingerprint.

Never retain raw pointer paths, full keystroke or command text, activity outside
ORISON, IP-derived location, exact identity, credentials, clipboard, local-file,
camera, microphone, contact, or advertising/analytics identifiers.

### Audit contract

Before implementation, document:

1. Every proposed field, its type, maximum size, precision, and narrative use.
2. Whether it belongs in the request-bearing cookie or browser-only storage.
3. Retention duration, migration from version 1, malformed-state behavior, and
   total storage budget.
4. What the server, Cloudflare edge, browser JavaScript, and visitor can observe.
5. How `/erase/` removes every store and how `privacy.txt` explains it plainly.
6. Which operator composition consumes the field and why existing state is
   insufficient.

### Boundaries

- “More local data” must mean deeper interaction history, not more identifying
  machine traits.
- Do not persist a raw machine profile, exact text input, or high-resolution
  behavioral telemetry.
- Do not add analytics, third-party scripts, server profiles, cross-browser
  correlation, or consent-sensitive collection without a new explicit decision.
- Any cookie-schema or storage-mechanism change requires migration tests and an
  ADR before feature implementation.
- The operator redesign must transform retained evidence into interpretation;
  it must not become a larger diagnostics dashboard.

### Success criteria

- A written data inventory and threat/privacy review exists before code changes.
- Each retained field drives a concrete route mutation or interaction and has a
  documented precision ceiling.
- Trace erasure removes all narrative storage and a fresh browser remains fresh.
- Existing version-1 traces migrate without silent loss.
- The operator becomes more intimate and unsettling while exposing less raw
  diagnostic inventory as its dominant visual form.

### Accepted implementation contract

The complete current/proposed field inventory, architecture comparison,
migration matrix, route-consumer matrix, threat/privacy review, trace-erasure
contract, and rollback strategy are recorded in
`docs/LOCAL_TRACE_AUDIT.md`. ADR 0007 is Accepted. The approved implementation
migrates the request-bearing version-1 cookie into a bounded browser-only
version-2 record, retains four coarse ORISON-only observations, moves new
witness tokens to URL fragments, and gives erasure a cross-tab contract. It is
merged on `main` through pull request 26 and deployed at `abb011c`.

## Milestone 8: Apparent Transfer Log

Status: Deployed with ADR 0009; replacement placement merged through pull request 41 with ADR 0013

### Objective

Use a dense, rapid terminal operation to create the impression that far more
material is being transferred, reconstructed, or attached than the visitor
expected from their command.

The fear should come from losing the ability to follow the operation and from
recognizing fragments of their own trace inside it. No file may actually be
installed or downloaded beyond ordinary page assets, and the interface must not
claim otherwise as a technical fact.

### Candidate event

- An explicit root or mount-terminal command begins a short stream of recovered
  paths, inode repairs, checksums, ownership changes, links, permissions,
  response sectors, and observer-record attachment.
- The first lines look like an ordinary archive operation. The stream then
  exceeds the apparent source archive, introduces records derived from the
  visitor's route, and ends with one clear operation that changes what the next
  page means.
- Output order and selected lines derive from explicit local state so repeat
  traces receive authored differences rather than random noise.
- The stream may accelerate beyond comfortable reading, but visitors who catch
  individual lines should find real relationships to prior actions rather than
  filler or generic hacker text.

### Boundaries

- Do not trigger a browser download, create a local file, request filesystem
  access, imitate operating-system security UI, or claim actual installation.
- Do not use fake malware warnings, ransomware language, package-manager brand
  names, or commands implying the visitor's host was modified.
- Keep the output inside ORISON's recovery, mount, reassignment, and retained
  record vocabulary.
- Do not replace the initial terminal's restrained opening with immediate noise;
  the event must be earned by an explicit command or later trace state.
- Under reduced motion, render the completed log immediately or in a small
  number of discrete phases without rapid scrolling.
- Do not flood screen-reader live regions with every transient line; expose a
  concise operation status and final result semantically.

### Success criteria

- The event initially resembles a transfer or installation while remaining
  technically honest about browser capabilities.
- At least several visible lines correspond to real retained route, answer, or
  archive state.
- The final readable line changes interpretation or progression; the stream is
  not decorative loading animation.
- Keyboard operation, narrow mobile, reduced motion, silent use, browser Back,
  and trace erasure remain valid.
- No download, filesystem API, permission request, external request, or new
  privacy behavior occurs.

### Accepted implementation contract

The selected operation remains in the late root terminal. The sole first
`unpack orison.zip` now performs the complete archive recovery without
trace-derived future evidence. After occupied Operator and five retained
answers, `reconcile response 00000000` accelerates through response sectors
derived from the bounded version-2 trace. Completion alone adds
`response-attached`, changes later root boot language, and exposes a
response-source record in Archive's left operational column without changing
the stable recovered-record index.

Replay uses reconciliation and loses acceleration and the moment of
reassignment. Reduced motion receives one completed composition. Transient
visual lines are excluded from live announcements; one polite status announces
start/review and completion. The accepted trigger/state/replay and rollback
matrices are in `docs/APPARENT_TRANSFER_LOG.md`; ADR 0013 supersedes ADR 0009's
placement while retaining the original state and privacy boundaries.

## Milestone 9: Parent Process

Status: Implemented, merged through pull request 34, and deployed in `94ffb657`

### Objective

Give the recovered directory one consequential maintenance action. The visitor
should believe they are releasing a blocked orphan, then discover through
operational evidence that the orphan resumed under the current trace instead.

### Visitor-facing interaction

- After both `operator-occupied` and `response-attached`, the archive exposes a
  narrow parent-process interlock between its source record and object index.
- The only action is `release orphan 00000000`.
- Activation briefly hands the scheduler from the unresolved input wait to the
  current trace. The process lanes and recovered-object states change together.
- Completion removes the action and leaves a persistent receipt: the orphan was
  released, a replacement parent was accepted, and the wait remains active.
- On revisit, the completed composition is present immediately. The transition
  and control do not replay.

### State and interpretation

- Add one allowlisted version-2 flag: `orphan-released`.
- The flag records only completion of the explicit archive action. It retains
  no timing, selected object, pointer data, command text, or machine profile.
- Version-1 migration must exclude the flag, as legacy pages could not have
  produced this event.
- Existing erasure and multi-tab behavior remove the flag with the full trace.
- The archive learns only that the subject chose to intervene. Re-parenting the
  process to the trace makes that choice consequential without identifying the
  visitor or deciding whether the parent relationship is literal.

### Placement and stable anchors

- The interaction belongs in the archive because it changes both the scheduler
  fabric and the recovered records. Root owns recovery, Operator owns authority,
  and the Horizon remains an observation-only scale rupture.
- Preserve object numbers, names, links, first-room hierarchy, Operator return,
  Camera/Weather Back behavior, and the response-source record.
- Do not add a route, second choice, sound, permission, dependency, external
  request, backend behavior, schema version, or another manifestation.

### Accessibility and responsive contract

- Use one native button with visible keyboard focus and one concise polite
  status. Do not announce every transient process-line change.
- Reduced motion resolves the handoff immediately and retains the same final
  evidence without an animated transfer.
- Narrow layouts stack the interlock without horizontal overflow or obscuring
  any recovered-object link.
- Storage-unavailable mode may show the session result but cannot promise a
  durable revisit, matching the accepted version-2 fallback contract.

### Success criteria

- The interlock is unavailable before both earned trigger conditions.
- Pointer and keyboard activation produce the same one-time completion flag.
- Process lanes and recovered records visibly enter one coherent parented state.
- Reload and later archive visits show the completed receipt without replay.
- Legacy migration, malformed/oversized state handling, erasure, browser Back,
  invitation isolation, mobile, reduced motion, local links, and browser-error/
  request boundaries continue to pass.

### Implemented result

- Added one late archive interlock gated by `operator-occupied` plus
  `response-attached`; no control is exposed before both conditions exist.
- Keyboard or pointer activation runs one concise seven-lane handoff and writes
  `orphan-released` only when the handoff completes.
- Completion changes all scheduler lanes and existing record states to one
  inherited parent relationship while preserving names, links, first-room
  source order, response evidence, and route behavior.
- Reload and later archive visits render the completed receipt immediately;
  the action and transition cannot replay.
- Legacy migration excludes the version-2-only flag. Existing erasure removes
  it across tabs, and storage-unavailable behavior remains ephemeral.
- Review captures cover ready/completed desktop and 375×812 mobile states.
- Local and production-image Playwright journeys, strict-CSP execution, reduced
  motion, asset digests, local references, browser errors, external requests,
  nginx configuration, dot-path denial, and container health passed.
- No route, schema version, permission, sound, dependency, backend, external
  request, portrait, manifestation, or privacy-boundary change was added.

## Post-program expansion pool: fragment ecology

Status: Speculative

Reference study:
[Wired Sound for Wired People](https://fauux.neocities.org/).

This reference is useful for its high-level web structure: a legible public
surface opens into a much larger collection of fragments; interface grammar
changes abruptly between directory, login, gallery, counter, puzzle, nearly
empty page, and missing-page states; numbered collections imply absent entries;
and accumulated interface eras make the site feel lived-in rather than centrally
redesigned.

These are structural observations only. Future ORISON work must not copy that
site's code, writing, imagery, music, names, page layouts, or exact interactions.
Any selected idea must be rebuilt from ORISON's own systems language, state
model, privacy contract, and narrative inversion.

### Candidate: operational fragment index

Expose a large, terse index of recovered labels. Most entries are unavailable,
reassigned, circular, or unresolved; a small subset resolve according to the
visitor's local trace. The index should imply much greater depth without
requiring dozens of complete routes.

The strange part is not merely that many paths exist. It is that the archive
appears to know which incomplete labels the visitor is likely to test.

### Candidate: missing sequence

Create a numbered object family with deliberate gaps. The visitor can access
only several members, and the cookie records which missing number they attempt
to resolve first. On return, the sequence changes around that attempted gap, as
if the absent object moved rather than opened.

Do not use the existing mechanical apertures as the repeated content of the
sequence.

### Candidate: assigned access state

Present a restricted operational surface that assigns a role from prior
behavior instead of accepting credentials. It must not imitate a real account
system, request secrets, or suggest actual authorization. The unsettling result
is that the visitor's role was already selected before they used the control.

Possible local classifications include peripheral, retained, suppressed,
substitute, or visible to one subsystem but absent from another.

### Candidate: nearly empty route

Use one route with almost no visible document: a single retained control,
coordinate, timestamp, process state, or changing absence against a large field.
Cookie state determines whether the missing content is unloaded, erased,
withheld, reassigned, or already transferred.

The route must remain accessible and purposeful. Sparseness should concentrate
meaning, not hide an unfinished page.

### Candidate: observation quota

A page counts locally inspected frames, records, or signal windows. The number
does not reward completion; it changes what the page is permitted to show and
eventually suggests the quota belongs to the archive rather than the visitor.

The counter must correspond to real local interactions and remain erasable with
the trace.

### Candidate: contradictory interface eras

Allow connected routes to appear built by different generations of the same
system: obsolete recovery utility, administrative record, spatial diagnostic,
image study, or near-empty monitor. Failed migrations, superseded labels, and
incompatible document formats should imply accumulated history without a lore
dump.

Abrupt medium changes are encouraged when they add a new interaction or
inference. They must not become arbitrary theme changes.

### Candidate: self-authored dossier

Let the same stable routes become substantially different documents as the
first-party cookie accumulates order, hesitation, repeated access, chosen
answers, and conspicuous absences. A camera record may become a navigation map;
a staff file may become a decision history; a weather report may claim that an
already completed action was forecast. The route should not merely mention the
visitor—the record itself should exist because of the visitor's behavior.

Later records may make specific, eerie, and occasionally contradictory claims
about preferences or decision style. These must remain deterministic fictional
interpretations of visible forced choices, never medical claims, hidden
fingerprinting, or assertions of real identity. The archive may be confidently
wrong; another route should eventually expose the evidence or contradiction
that produced its claim.

### Candidate: decaying resources

An object initially exposes several internal resources. Across explicit,
cookie-backed revisits, some become unavailable, redirect into residue, exchange
labels, or claim they were never linked. Decay must be authored and
deterministic from local state, never accidental broken links.

### Candidate: 404 ecology

Treat families of missing paths as different operational regions. Repeated
probes into one naming pattern may create a distinct missing-page composition,
temporarily resolve a route, or produce a callback in another recovered object.

The path itself is the interaction input. Do not add a conventional site map
that explains the regions.

### Candidate: accumulated archive age

Use contradictory dates, obsolete interface conventions, dead internal
references, and maintenance residue to make ORISON feel revised over a long
period. Age should emerge from incompatible evidence and failed transitions,
not from a document explaining the chronology.

### Selection rules

Before promoting any candidate into a milestone, define:

1. What the visitor believes the surface is.
2. What ORISON learns, causes, or reclassifies.
3. Which explicit local state condition earns it.
4. What stable anchor reveals that the page or route changed.
5. What happens on another revisit.
6. Why an existing route cannot provide the same interaction or inference.
7. How mobile, keyboard, reduced motion, trace erasure, and cookie migration
   remain valid.

## Ideas intentionally deferred

- Cross-visitor effects beyond unverified invitation tokens.
- Accounts or exact identity.
- Downloadable artifacts.
- Subdomain- or HTTP-status-driven narrative systems.
